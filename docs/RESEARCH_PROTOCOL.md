# CVS Lab Research Protocol

## Objective

Measure how chess capability changes as we vary learned capacity, explicit semantic structure, supervision, and executed search compute.

The lab starts deliberately small and scales only after controlled evidence justifies the next step.

## Independent axes

### Learned capacity

Track exact learned parameter count. Do not use hidden width as a proxy when comparing different architectures.

### Representation

Examples:

- raw piece-square inputs;
- deterministic CVS geometry;
- motif families;
- strategic/positional families;
- modular semantic branches;
- hybrid raw + semantic designs.

### Executed compute

Examples:

- fixed nodes;
- depth;
- wall-clock budget;
- specialist/helper search;
- repeated/recurrent computation.

### Training signal

Examples:

- scalar evaluator target;
- deterministic board facts;
- motif/strategy labels;
- position/move/transition labels;
- shallow CVS search;
- deep CVS search;
- game outcome;
- sparse Stockfish/external-oracle audit labels.

Never treat these axes as interchangeable.

## Generations

A generation is a frozen scientific regime, not merely the next model trained.

A new generation is required when changes are large enough that direct within-generation ablations would become misleading, such as a new training corpus contract, representation regime, or fundamentally different architecture family.

Within a generation, freeze enough of the following for clean comparison:

- source engine identity;
- dataset manifests and split identities;
- label semantics;
- trainer semantics;
- evaluation suites;
- search profile for game gates;
- hardware/resource policy where relevant.

## Experiment identities

- `H####` hypothesis
- `A####` ablation
- `M####` model artifact
- `D####` dataset
- `T####` training recipe
- `E####` evaluation protocol
- `R####` run

An ablation is not a run. Multiple seeds or repetitions of the same intervention create multiple `R####` records under one `A####`.

## Ablation signature

Human display:

`A#### FAMILY-GEN-PARAMS @ BASELINE : OVERRIDES`

Only deviations from the baseline belong in the compact display name. The full machine configuration records all effective settings.

Examples:

- `A0001 NNUE-G01-P771 @ RAW : H=1`
- `A0017 NNUE-G01-P12K @ RAW : H=16`
- `A0062 NNUE-G03-P25K @ HYBRID : KING_SAFETY=0`

## Initial first-principles ladders

### Raw NNUE

For a 768-input, one-hidden-layer evaluator, begin with a width ladder from H=1 upward. Record exact serialized parameter counts rather than trusting formula-only estimates.

Recommended first sweep:

H = 1, 2, 4, 8, 16, 32, 64, 128, 256.

### Geometry evaluator

Run an analogous tiny-to-large sweep using the frozen semantic geometry vector. Start at H=1. Do not skip tiny models because they appear obviously too weak; the purpose is to locate emergence thresholds empirically.

### Matched-budget comparison

After the two control curves exist, compare raw-only, geometry-only, and hybrid candidates at approximately matched exact parameter budgets.

## One-variable discipline

Prefer one-variable interventions whenever practical.

When testing interactions, declare them explicitly rather than silently changing multiple fields. For example, test A, B, and A+B as separate ablations.

## Evidence states

- `PROPOSED`
- `RUNNING`
- `SUPPORTED`
- `REJECTED`
- `INCONCLUSIVE`
- `SUPERSEDED`
- `INVALID`

`INVALID` is reserved for evidence/integrity failures. Weak model performance is not invalid evidence.

## Required run evidence

Every run must record at minimum:

- hypothesis and ablation identity;
- source engine commit;
- effective engine/search identity;
- model architecture and exact parameter count;
- model hashes;
- dataset manifest and split hashes;
- taxonomy/facts-registry identity when semantic features are used;
- training recipe identity;
- seeds;
- hardware;
- executed compute/resources;
- evaluation suite identity;
- raw metrics and uncertainty;
- integrity checks;
- artifact hashes.

## Standard finding card

Every concluded ablation produces:

### Hypothesis

What was expected?

### Control

What remained frozen?

### Intervention

Exactly what changed?

### Evidence

What measurements were collected?

### Result

SUPPORTED / REJECTED / INCONCLUSIVE / INVALID.

### Interpretation

What does the evidence justify saying?

### Non-claim

What does it not establish?

### Next experiment

What is now justified by the evidence?

## Compute discipline

Record compute as a research variable.

Track at least:

- CPU seconds/hours;
- GPU seconds/hours where used;
- search nodes;
- labels generated by tier;
- expensive external-oracle labels;
- accepted vs discarded examples.

The lab should be able to compare capability or information gained per unit compute, not only absolute strength.

## Data discipline

Keep semantic facts, bounded tactical facts, search-derived values, game outcomes, and external-oracle labels as separate provenance classes.

Do not expose future/search/outcome information as static model input unless that is the explicit intervention under test.

## Scaling rule

An idea does not earn a larger model or larger corpus merely because it is interesting.

It advances only when smaller controlled tests justify spending more compute.

Negative findings are permanent research assets and remain visible in the GUI and reports.
